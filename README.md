# Прием USDT в BNB Smart Chain и TRON

Самостоятельный платежный сервис на TypeScript и Node.js для сайта, бота или другого проекта. Создает счет с отдельным адресом, проверяет подтвержденные переводы и уведомляет ваш бэкенд подписанным webhook. Средства поступают на адреса вашего кошелька. Покупатель видит реквизиты в вашем приложении и отправляет перевод из своего кошелька.

Сервис читает блокчейн через Alchemy Chain API. RPC для обеих сетей используют один ключ Alchemy оператора. Собственная нода не требуется. Один экземпляр сервиса обслуживает несколько проектов с отдельными ключами доступа, webhook и адресами приема. [Сети Alchemy Chain API](https://www.alchemy.com/docs/reference/node-supported-chains)

| `chain` | Актив в основной сети | Контракт | Десятичных знаков |
| --- | --- | --- | ---: |
| `bsc` | Binance-Peg BSC-USD (USDT BEP20) | `0x55d398326f99059ff775485246999027b3197955` | 18 |
| `tron` | USDT TRC20 (Tether в TRON) | `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` | 6 |

При оплате указывайте сеть вместе с токеном. Сервис засчитывает переводы по указанным контрактам в финализированных блоках BSC и подтвержденных блоках TRON. Проверка зависит от данных и доступности Alchemy. [BNB Chain Finality API](https://docs.bnbchain.org/bnb-smart-chain/developers/json_rpc/bsc-api-list/) · [Подтверждение в TRON](https://developers.tron.network/docs/confirmation-semantics)

## Установка и настройка

Установите Node.js версии 22.16 или новее. Выполните следующие команды из каталога репозитория. Для административных команд ключ Alchemy не нужен.

```sh
npm ci
npm run payments:admin -- init
npm run payments:admin -- project --id shop --webhook https://shop.example/payments/webhook --credentials runtime/payments/shop.credentials.json
```

Замените `shop` и `https://shop.example/payments/webhook` на идентификатор проекта и HTTPS-адрес обработчика. Для каждого дополнительного проекта повторите команду `project` с отдельными реквизитами.

`init` создает `runtime/payments/service.json` с параметрами SQLite и ключом шифрования. `project` сохраняет `projectId`, `apiKey` и `webhookSecret` в отдельном файле. Используйте `PAYMENTS_CONFIG`, если нужен другой путь к конфигурации сервиса. Административным командам этот путь также можно передать через `--config`. Храните конфигурацию, учетные данные и базу вне Git с доступом только для нужных процессов и операторов. На Linux новые файлы создаются с режимом 0600, каталоги - 0700. Для существующих файлов проверьте права отдельно, а на Windows настройте ACL.

### Адреса приема

Для каждой сети и проекта подготовьте собственные адреса. Сервис закрепляет выданный адрес за одним счетом, включая закрытые и просроченные счета.

**Импорт списка.** Сохраните новые неиспользованные адреса из кошелька по одному на строку. Проверьте на стороне кошелька, что можете восстановить доступ к ним.

```sh
npm run payments:admin -- addresses --project shop --chain bsc --file runtime/payments/bsc-addresses.txt
npm run payments:admin -- addresses --project shop --chain tron --file runtime/payments/tron-addresses.txt
```

Пополняйте список новыми адресами по мере выдачи счетов. При исчерпании списка создание новых счетов для этой пары проекта и сети возвращает HTTP 503.

**Автоматическая выдача из xpub.** Выделите отдельный HD-аккаунт для каждого проекта. Экспортируйте из кошелька публичную внешнюю ветку `m/44'/60'/<account>'/0` для BSC или `m/44'/195'/<account>'/0` для TRON. Сервис принимает `xpub` основной сети на глубине 4 с последним индексом 0. Адреса получаются добавлением `/0`, `/1` и следующих индексов к пути ветки. Сверьте полный путь и первые несколько адресов в кошельке. Из xpub нельзя определить весь родительский путь.

Сохраните параметры публичной ветки TRON в JSON-файле.

```json
{
  "xpub": "<XPUB_ПУБЛИЧНОЙ_ВЕТКИ>",
  "firstAddress": "<ПОЛНЫЙ_АДРЕС_ВЕТКИ_С_ИНДЕКСОМ_0>",
  "derivationPath": "m/44'/195'/0'/0"
}
```

```sh
npm run payments:admin -- hd-branch --project shop --chain bsc --file runtime/payments/bsc-public-branch.json
npm run payments:admin -- hd-branch --project shop --chain tron --file runtime/payments/tron-public-branch.json
npm run payments:admin -- address-manifest --project shop --chain tron --out runtime/payments/tron-address-manifest.json
```

При импорте сервис сверяет адрес с индексом 0. Затем он создает пул из 20 адресов и при выдаче счета пополняет его до 20, когда доступно меньше пяти. Seed-фраза, приватные ключи и подпись транзакций остаются в кошельке. Поскольку xpub раскрывает адреса ветки, храните его в приватной конфигурации.

Подключение MetaMask и получение адреса аккаунта не дают xpub внешней ветки. Стандартный экспорт такой ветки через интерфейс MetaMask не проверен. Если ваш кошелек не поддерживает нужный экспорт, используйте импорт списка публичных адресов. [Документация по экспорту аккаунта MetaMask](https://support.metamask.io/configure/accounts/how-to-export-an-accounts-private-key/)

### Запуск

В Alchemy Dashboard создайте приложение с Chain API и включите в нем обе сети, BNB Smart Chain Mainnet и Tron Mainnet. Для `payments:start` передайте ключ этого приложения в переменной окружения `ALCHEMY_API_KEY`. Сервис обращается к `bnb-mainnet.g.alchemy.com` и `tron-mainnet.g.alchemy.com`. Храните ключ в секретах процесса сервиса. Бэкенды подключенных проектов используют отдельные ключи, созданные командой `project`. Покупателю достаточно реквизитов счета. [Создание ключа Alchemy](https://www.alchemy.com/docs/create-an-api-key) · [Разрешенные сети приложения](https://www.alchemy.com/docs/admin-api/apps/update-app-network-allowlist) · [Alchemy TRON Solidity HTTP API](https://www.alchemy.com/docs/chains/tron/tron-solidity-http-api-endpoints/tron-solidity-http-api-endpoints/get-latest-block)

В Bash можно ввести ключ без отображения и записи значения в историю команд.

```bash
read -r -s -p 'Ключ Alchemy: ' ALCHEMY_API_KEY
printf '\n'
export ALCHEMY_API_KEY
npm run payments:start
unset ALCHEMY_API_KEY
```

В PowerShell 7.2 и новее используйте ввод с маской.

```powershell
$env:ALCHEMY_API_KEY = Read-Host -Prompt 'Ключ Alchemy' -MaskInput
try {
    npm run payments:start
} finally {
    Remove-Item Env:ALCHEMY_API_KEY -ErrorAction SilentlyContinue
}
```

Проверьте состояние сервиса в другом терминале.

```sh
curl http://localhost:3501/health
curl http://localhost:3501/ready
```

`/health` показывает, что процесс отвечает. `/ready` возвращает HTTP 200, когда сканеры обеих сетей догнали подтвержденные блоки, и HTTP 503 в остальных случаях. Первый запуск начинает отслеживание с текущей подтвержденной вершины каждой сети. После перезапуска сканирование возобновляется с сохраненной позиции.

Alchemy измеряет пропускную способность в Compute Units в секунду на аккаунт. Обе сети расходуют квоту при сканировании блоков, даже при отсутствии новых счетов. При HTTP 429 сервис повторяет чтение после паузы с сохраненной позиции. Следите за квотой и отставанием сканеров. [Лимиты и HTTP 429 Alchemy](https://www.alchemy.com/docs/reference/throughput)

Сервис слушает loopback на порту 3501. Для удаленных бэкендов установите HTTPS reverse proxy рядом с сервисом. База SQLite требует локального диска и одного экземпляра сервиса на файл базы.

## Подключение проекта

Ваш бэкенд проверяет сессию пользователя, находит его заказ и берет сумму из своих данных. Затем он создает счет в платежном сервисе. Храните `apiKey` на бэкенде. Передайте интерфейсу только сведения, необходимые для оплаты и показа статуса.

```http
POST /v1/invoices
Authorization: Bearer <PROJECT_API_KEY>
Content-Type: application/json
Idempotency-Key: order-701-v1

{"userId":"user-125","orderId":"order-701","chain":"tron","amount":"10.00"}
```

Сумма передается строкой с максимум шестью знаками после точки, больше нуля и не больше 1 000 000 USDT. Сервис возвращает `{ "invoice": { ... } }` с HTTP 201, либо HTTP 200 при повторе того же запроса. Храните `invoice.id` и исходный `Idempotency-Key` вместе с заказом. При сетевом сбое повторяйте запрос с тем же ключом и теми же параметрами. Повторное использование ключа с другими данными или создание нового счета для уже связанного заказа возвращает HTTP 409.

Покажите покупателю сеть, сумму, полный адрес и срок счета. Срок действия составляет 30 минут. Бэкенд получает статус счета по следующему запросу.

```http
GET /v1/invoices/<INVOICE_ID>?userId=user-125
Authorization: Bearer <PROJECT_API_KEY>
```

Сервис сверяет проект по ключу и владельца по `userId`. До трех новых счетов за скользящие 30 минут доступны для каждого пользователя в каждом проекте. При HTTP 429 учитывайте `Retry-After`. При HTTP 503 проверьте готовность сети или наличие адресов в пуле. Запросы через один reverse proxy делят ограничение 60 запросов в минуту на один адрес TCP-подключения.

## Уведомления об оплате

Сервис отправляет JSON методом POST на HTTPS-адрес проекта, указанный в команде `project`. Для приемника нужен публично разрешаемый домен на стандартном порту HTTPS. Храните секрет только на сервере и используйте URL без учетных данных или токенов в строке запроса. В теле приходят `eventId`, `type`, `createdAt`, снимок `invoice` и сведения о переводе `transfer`.

- `payment.paid` означает, что подтвержденные переводы в пределах срока покрыли сумму. Статус счета `paid` или `overpaid`.
- `payment.review` сообщает о неполной, поздней или дополнительной оплате. Обрабатывайте ее отдельно от автоматической выдачи покупки.

Сервис передает подпись и ее параметры в заголовках запроса.

```text
X-Payment-Event-Id: <EVENT_ID>
X-Payment-Timestamp: <UNIX_SECONDS>
X-Payment-Signature: v1=<HMAC_SHA256_HEX>
```

Подпись вычисляется как HMAC-SHA256 от строки времени, точки и исходных байтов тела запроса. Используйте значение `webhookSecret` как строковый ключ HMAC. Принимайте время в пределах пяти минут от текущего. Сравнивайте подписи за постоянное время и разбирайте JSON после проверки подписи. Переупаковка JSON меняет подписанные байты.

Минимальный пример проверки на Node.js. `rawBody` должен быть буфером исходного запроса до JSON-парсинга.

```js
import { createHmac, timingSafeEqual } from 'node:crypto'

export function verifyPaymentSignature(secret, timestamp, signature, rawBody) {
  if (
    typeof timestamp !== 'string' ||
    !/^\d{10}$/.test(timestamp) ||
    Math.abs(Date.now() - Number(timestamp) * 1000) > 300_000 ||
    typeof signature !== 'string' ||
    !/^v1=[0-9a-f]{64}$/.test(signature) ||
    !Buffer.isBuffer(rawBody)
  ) {
    return false
  }

  const expected = createHmac('sha256', secret)
    .update(timestamp + '.')
    .update(rawBody)
    .digest()
  const actual = Buffer.from(signature.slice(3), 'hex')
  return timingSafeEqual(expected, actual)
}
```

После проверки подписи обработайте событие в бэкенде проекта.

1. Сверьте `eventId` в теле с `X-Payment-Event-Id`.
2. Найдите сохраненный заказ. Сверьте `invoice.id`, `projectId`, `userId`, `orderId`, `chain`, `asset`, `tokenContract` и сумму в минимальных единицах `amountAtomic` с данными заказа. Перед выдачей покупки убедитесь, что `type` равен `payment.paid`, статус равен `paid` или `overpaid`, а `receivedAtomic` покрывает `amountAtomic`. Сравнивайте минимальные единицы как целые числа, например `BigInt`.
3. В одной транзакции базы проекта запишите `eventId` с уникальным ограничением и примените оплату. Добавьте отдельное уникальное ограничение на выдачу покупки по заказу. Для подтвержденного дубликата верните HTTP 2xx без повторной выдачи.
4. Верните HTTP 2xx после фиксации транзакции. Если запись временно недоступна, верните ошибку, чтобы сервис повторил доставку.

Подтвержденный перевод учитывается один раз по сочетанию сети, хеша транзакции и индекса события. Два разных события одной транзакции обрабатываются отдельно. Очередь webhook хранится в SQLite. Сервис отправляет события одного проекта последовательно, а нескольких проектов - параллельно. После таймаута или перезапуска событие может прийти повторно с тем же `eventId` и новой подписью. Для новых событий повторная обработка того же перевода после восстановления резервной копии сохраняет `eventId`, если счет и проект остались теми же. Учет обработанных событий должен сохраняться в базе вашего проекта.

## Проверки и эксплуатация

```sh
npm run payments:check
```

Команда запускает тесты и проверку типов. Тесты проверяют запуск с имитированным RPC, привязку счетов, проверку переводов, обработку повторов, изоляцию проектов и восстановление после перезапуска. Для тестов достаточно синтетических данных, проверка с личным ключом Alchemy и приемочные переводы в них не входят. В отдельной проверке на общедоступном демонстрационном доступе Alchemy удалось прочитать подтвержденный блок TRON. BNB Smart Chain вернула HTTP 429. Для работы с реальными платежами отдельно проверьте адреса и восстановление кошелька, HTTPS и webhook, задержку сканирования под нагрузкой и небольшие приемочные переводы в обеих сетях. Непрерывный просмотр блоков в обеих сетях может выйти за месячный лимит бесплатного плана. Оцените расход CU по фактическому трафику. [Тарифы Alchemy](https://www.alchemy.com/pricing) · [Стоимость запросов](https://www.alchemy.com/docs/reference/compute-unit-costs)

Используйте согласованные резервные копии SQLite и сохраняйте ключ шифрования отдельно от базы. Для HD-веток сохраняйте манифест с путями адресов и журнал выданных счетов. После восстановления старой копии сверяйте уже выданные адреса перед возобновлением выдачи. Транзакции блокчейна показывают поступления, поэтому адреса неоплаченных счетов восстанавливаются по вашим записям.

Сервис работает в режиме watch-only. Вывод и возврат выполняет отдельный кошелек. Для перемещения BEP20 с адресов приема нужен BNB для комиссии. Для TRC20 учитывайте активацию аккаунта и ресурсы TRON. [Bandwidth и Energy в TRON](https://developers.tron.network/docs/bandwidth-and-energy)
